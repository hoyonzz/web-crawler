## 1. 한글 인접 영문 키워드 매칭 실패 — `\b`의 유니코드 한계

**현상**
`"python개발자"`처럼 영문 키워드가 한글에 바로 붙은 공고에서 `\bpython\b`가 매칭에 실패했다. 띄어쓰기 없이 작성된 다수의 유효 공고가 1차 필터에서 누락됐다.

**원인**
파이썬 `re` 모듈은 유니코드 모드에서 한글을 단어 문자(`\w`)로 취급한다. 따라서 `"python개발"`에서 `'n'`과 `'개'`는 둘 다 단어 문자로 인식되어 그 사이에 단어 경계(`\b`)가 존재하지 않는다. 결과적으로 `\bpython\b`의 우측 경계 조건이 성립하지 않아 매칭에 실패한다.

**해결**
`\b` 대신 라틴 문자 기준의 부정 전후방 탐색으로 전환했다.

```python
pattern = rf'(?<![a-zA-Z]){re.escape(kw)}(?![a-zA-Z])'
```

키워드의 좌우가 영문 알파벳이 아닐 때만(= 한글·숫자·공백·기호일 때) 독립된 단어로 인정한다. 이로써 `"python개발"`·`"python3"`는 매칭하면서, `"email"`의 `'ai'`처럼 영문 단어 내부에 우연히 포함된 경우는 차단한다.

**배운 점**
`\b`는 ASCII 텍스트를 전제로 설계된 도구다. 다국어가 섞인 텍스트에서는 "단어 경계"의 정의를 도메인에 맞게(여기서는 '라틴 문자 인접 여부') 직접 설계해야 한다.

## 2. 점수 인플레이션 — 배수(Multiplier) 로직의 숨은 강제 룰

**현상**
설계 의도상 "Growth 키워드(가중치 3.0) 2개 이상이면 통과(6.0 > 임계치 5.0)"가 성립해야 했지만, 실제로는 Growth 키워드만으로는 아무리 많이 맞춰도 통과하지 못했다.

**원인**
기존 점수 로직에 "그룹당 최대 1.5배"의 한도 배수가 걸려 있었다. 이 때문에 가중치 3.0짜리 그룹은 키워드를 아무리 많이 맞춰도 `3.0 × 1.5 = 4.5`점에서 성장이 멈췄다. 결과적으로 임계치 5.0을 넘으려면 반드시 5.0짜리 키워드(Core)가 1개 이상 있어야 하는, **의도하지 않은 숨은 강제 룰**이 발생했다.

**해결**
복잡한 배수 공식을 제거하고, 매칭된 키워드 수만큼 가중치를 정직하게 더하는 선형 합산으로 변경했다.

```python
raw_score += (matched_count * base_weight)
```

이로써 "Growth 2개 = 6.0 > 5.0 통과"가 수학적으로 성립하도록 설계 의도를 복원했다.

**배운 점**
점수 공식에 상한·배수 같은 비선형 보정을 넣으면 직관과 실제 동작이 쉽게 어긋난다. 임계치 기반 판정에서는 "어떤 입력이 통과하는가"를 직접 손으로 계산해 검증하는 과정이 필요하다.

## 3. 모듈 간 API Contract(0.0~1.0) 파괴와 점수 정규화

**현상**
점수 산정을 원점수(예: 13.0, 18.0) 반환으로 바꾸자, 0.0~1.0 범위를 기대하는 하위 모듈(Notion 적재·정렬 등)에서 값이 깨질 위험이 드러났다.

**원인**
판정 로직을 절대 점수(threshold) 비교로 바꾸면서, 반환 점수의 스케일도 함께 0~1에서 원점수로 바뀌었다. 그러나 이 점수를 소비하는 쪽은 여전히 0.0~1.0(비율)을 가정하고 있었다 — 모듈 간 암묵적 계약(API Contract)이 깨진 것이다.

**해결**
판정은 원점수로 하되, 반환값은 정규화해 계약을 지키도록 분리했다.

```python
TARGET_MAX_SCORE = 25.0
normalized_score = min(raw_score / TARGET_MAX_SCORE, 1.0)
```

처음에는 `TARGET_MAX_SCORE = 10.0`으로 계약(0~1)을 복원했으나, 키워드 2~3개만 맞아도 점수가 1.0에 조기 포화돼 정렬 변별력이 사라지는 것을 발견했다. 이에 기준값을 25.0으로 상향해 점수가 더 넓은 구간에 분포하도록 재튜닝했다.

**배운 점**
판정에 쓰는 내부 점수와 외부에 노출하는 반환 점수는 분리할 수 있다. 또한 정규화 기준값 하나가 다운스트림의 정렬·표시 품질을 좌우하므로, "0~1로 맞춘다"를 넘어 점수 **분포**까지 고려해야 한다.

## 4. LangChain + google-genai SDK 전환 시 재시도 예외 타입 미스매치

**현상**
Gemini 503(서버 일시 과부하) 대응으로 `tenacity` 재시도를 붙였으나, `google.api_core.exceptions`의 `ServiceUnavailable`·`ResourceExhausted`로 예외를 잡도록 작성하자 재시도가 한 번도 트리거되지 않았다. import는 통과해 에러 없이 "조용히" 첫 시도에 실패하고 끝났다.

**원인**
`langchain-google-genai` 4.0이 레거시 `google-generativeai`에서 통합 `google-genai` SDK로 전환되면서 예외 체계가 바뀌었다. 실제 발생 예외는 `google.genai.errors.ServerError`(부모: `google.genai.errors.APIError`)인데, 잡으려던 `ResourceExhausted`의 부모는 `google.api_core.exceptions.TooManyRequests`다. 두 계열은 상속 관계가 전혀 없어, `retry_if_exception_type`이 실제 예외를 하나도 매칭하지 못했다.

**해결**
공식 SDK 소스(`google/genai/errors.py`)로 예외 계층을 확인한 뒤, 재시도 조건을 SDK 버전 변화에 강한 방식으로 작성했다. 예외 메시지의 상태코드(429·5xx) 문자열로 일시적 에러를 판별하는 커스텀 predicate를 `retry_if_exception`에 연결하고, 재시도 동작은 503을 강제 발생시키는 Mock 테스트로 "대기 후 재시도"가 실제로 도는지 눈으로 검증했다.

**배운 점**
예외 기반 재시도는 import 통과만으로 검증되지 않는다. 잡으려는 예외 타입과 실제로 던져지는 예외 타입이 일치하는지를 반드시 실제 에러(또는 Mock)로 확인해야 한다. 특히 SDK 메이저 버전 전환 시 예외 계층은 호환되지 않을 수 있으므로, 타입 상속에 의존하기보다 상태코드 기반 판별이 더 견고하다.

## 5. URL 파라미터 추측 매핑의 함정 — 네트워크 탭 실측으로 규명

**현상**
잡코리아 크롤러에 신입 필터(`scd=I000,B000`)를 적용했는데도 수집 결과에 시니어·비개발 공고(결산, 보험영업, 조경 등)가 다수 혼입됐다. 필터 파라미터는 URL에 정상적으로 들어가 있었고 에러도 없었다.

**원인**
파라미터의 의미를 추측으로 매핑한 것이 원인이었다. `scd=I000,B000`은 경력 코드가 아니라 **지역 코드(서울·경기)**였고, 실제 경력 필터는 `careerTypeCode=1/3,4`(신입=1/3, 경력무관=4)라는 별도 파라미터였다. 즉 크롤러는 경력 필터를 한 번도 건 적이 없었다. 사이트 UI에서 필터를 직접 조작한 뒤 개발자도구 네트워크 탭에서 실제 AJAX 요청 URL을 캡처해 대조함으로써 규명했다.

**해결**
실측한 요청 URL 기준으로 `_build_list_url`을 재작성했다(`careerTypeCode=1%2F3%2C4` 추가, `scd`는 지역 코드로 의미 정정). 검증은 정성 판단이 아니라 **필터 ON/OFF의 서버 totalcount 대조**로 수행했다 — 필터 적용 시 1,218건 vs 미적용 시 4,274건으로, 파라미터가 서버에 실제 반영됨을 정량 확인했다.

**배운 점**
내부 API의 파라미터 이름은 의미를 보장하지 않는다. 추측 매핑 대신 브라우저에서 해당 필터를 실제로 조작하고 네트워크 탭의 요청을 캡처해 대조하는 것이 유일하게 확실한 방법이다. 또한 "필터가 적용됐는가"는 결과 목록을 눈으로 훑는 것보다 필터 유무에 따른 서버 응답 값(totalcount) 차이로 검증하는 편이 재현 가능하고 객관적이다.

## 6. '경력무관'의 두 얼굴 — LLM 판정과 룰 파서의 역할 분리

**현상**
LLM(Gemini)이 채용공고의 요구 경력을 판정하는 파이프라인에서, 헤더에 "경력 1-3년"이 명시된 공고가 '경력무관'으로 적재됐다. 프롬프트에는 이미 "본문의 명시적 연차를 1순위로 신뢰"하는 규칙이 있었는데도 발생했다.

**원인**
공고 자체가 모순 정보를 담고 있었다 — 헤더는 "경력 1-3년", 본문 자격요건은 "경력(연수무관)". LLM은 "본문 우선" 규칙을 정확히 따라 본문의 '연수무관'을 채택했고, 스키마의 '경력무관' 값으로 매핑했다. 근본 원인은 한국 채용공고에서 같은 '무관'이 정반대 의미로 쓰인다는 점이다: '경력무관'은 "신입도 지원 가능", '경력(연수무관)'은 "경력자만 받되 연차는 안 따짐"(=신입 불가). 이 의미 충돌이 스키마 정의를 뚫었다.

**해결**
두 계층으로 분리해 대응했다. ① 원티드처럼 헤더가 구조화된 공고는 정규식 룰 파서(`parse_career_from_header`)로 결정적으로 파싱해 LLM 판정을 덮어쓰도록 했다(override 패턴). 단 `[상단 요약 정보]` 마커가 있는 경우에만 개입하는 가드를 두어, 비정형 텍스트에 룰이 잘못 개입하지 않게 했다. ② 룰이 못 잡는 비정형 공고를 위해 스키마 description에 "'경력무관'과 '경력이되 연수무관'은 정반대 의미"라는 함정 규칙과 '경력직 추정' 규칙을 명시했다.

**배운 점**
기계적으로 확정 가능한 정보(구조화된 헤더의 연차 표기)를 확률적 모델에 맡길 이유가 없다 — 룰로 처리 가능한 영역은 룰로 확정하고, LLM은 판단이 필요한 비정형 영역만 담당하게 역할을 분리하는 것이 판정 일관성을 높인다. 또한 LLM의 "오판"처럼 보이는 결과가 실은 지시를 정확히 따른 결과일 수 있으므로, 프롬프트를 고치기 전에 입력 데이터와 규칙의 상호작용을 먼저 재구성해봐야 한다.
